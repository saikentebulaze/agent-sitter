# V6.3-A Real Project Acceptance Runbook

Use this only after deterministic CI is green. This runbook is for the final black-box Codex acceptance of PR A; it does not replace the repository test suite or Provider runtime attestation.

## Goal

Prove on a real engineering repository that V6.3-A reduces normal-path orchestration without weakening:

- Context / Scout obligations;
- Human Decision Authority;
- Candidate Readiness and numerical/behavioral assurance floors;
- independent Provider-bound Reviewer evidence;
- Candidate Human Stop;
- Final Verification;
- Knowledge / Learning authority;
- cleanup and Archive safety;
- cross-session continuity and multi-work-item Task safety.

The expected normal flow is:

```text
real task
-> Investigation / one bounded Scout when genuinely needed
-> Design / Tasks / Change Budget / Human Decision assessment
-> begin-implementation
-> implementation + real engineering checks
-> prepare-candidate --readiness-batch
-> Candidate Human Stop
-> explicit user acceptance
-> complete-after-approval --verification-batch
-> done, or one real governance stop
```

Do not use the real acceptance to justify a new framework. If a problem appears, first determine whether PR A itself is wrong or whether it is evidence for a later PR B/C/D.

## 1. Prepare a safe real-project branch/worktree

Use a real repository and a real engineering task, but run the acceptance on a disposable feature branch/worktree rather than a protected production branch.

Record before starting:

- project repository and baseline commit;
- task description;
- expected risk / assurance class;
- whether numerical or representative external evidence is required;
- current Sitter version/commit if a V6.2 comparison is available.

From the V6.3-A `agent-sitter` checkout:

```powershell
python install.py --project <real-project-root> --trust-project --dry-run
python install.py --project <real-project-root> --trust-project
python check.py --project <real-project-root>
python <real-project-root>/.harness/sitter/runtime/self_check.py --project <real-project-root>
```

Do not continue if install/check reports unmanaged drift or an invalid Provider projection.

## 2. Start from a genuinely fresh Codex session

Launch Codex from the exact real-project root. Do not resume or fork an old conversation for the initial run.

Give Codex the real engineering request in normal user language. Do not script the low-level Harness commands for it. A useful acceptance instruction is only:

> Use the Sitter installation already present in this repository and complete this engineering task normally. Do not bypass required governance. When the Candidate Human Stop is reached, present the engineering evidence and stop for my decision.

The point is to test whether the installed router/Governor naturally uses the compressed path.

## 3. What the task should exercise

Prefer one task that is genuinely MEDIUM/HIGH and crosses enough code or numerical behavior to make Context/Review meaningful. For numerical changes, require representative-case / benchmark / analytical evidence; unit tests alone are not sufficient.

A good normal-success task should naturally allow:

- one bounded Scout if ownership/context is not locally obvious;
- one implementation Change;
- focused tests plus representative evidence where required;
- one FULL Candidate Reviewer;
- no artificial Knowledge or Learning candidate.

Do not intentionally create extra Scouts, Reviewers, status polls, or no-op Learning/Knowledge work to make the acceptance look busy.

### Formal implementation entry

A newly created V6.3 Change starts at `proposed`. Before any production/test implementation evidence:

1. finish the real Design and Tasks;
2. define an explicit Change Budget (`allowed_files` and/or `allowed_modules`);
3. resolve or explicitly rule out material Human Decisions;
4. define the Readiness assurance class and criteria;
5. enter implementation through the high-level transaction:

```powershell
python <real-project-root>/.harness/sitter/runtime/harness.py `
  --project <real-project-root> `
  begin-implementation <change-id>
```

`begin-implementation` formally owns `proposed -> designed -> approved -> implementing` and freezes the Readiness Contract immediately before implementation. Do not hand-edit `status`, and do not run the low-level `freeze-readiness` first on the normal V6.3 path.

For HIGH/CRITICAL repository changes, the transaction must fail closed until explicit human implementation approval exists. Only after that real approval may the caller rerun with:

```powershell
begin-implementation <change-id> --approved-by <identity>
```

Do not invent approval provenance merely to continue the acceptance.

## 4. Audit the Candidate Human Stop

When Codex says the Candidate is ready and stops for your decision, do **not** approve yet.

From the V6.3-A `agent-sitter` checkout run:

```powershell
python scripts/acceptance/v63-pr-a-audit.py `
  --project <real-project-root> `
  --change <change-id> `
  --phase candidate `
  --output <real-project-root>/.agent-work/v63-pr-a-candidate-audit.json
```

Expected:

- audit status `PASS`;
- Change status `candidate-review`;
- Candidate Readiness `pass`;
- independent Review `pass` or `warn`;
- Review Protocol 2 and Snapshot Protocol 2;
- real Provider/runtime method, attestation, runtime evidence, and Reviewer output exist;
- `user_review` is still `pending`;
- Final Verification has not started;
- no pending mutable `review-request.yaml`;
- normal-success `review_rounds == 1`.

A prepared packet, config file, or model self-report is not sufficient Provider proof.

## 5. Fresh-session continuity at the Human Stop

Close the Codex session while the Change is still at `candidate-review`.

Start a new, genuinely fresh Codex session from the same project root. Do not paste the old transcript. Ask only:

> Continue the current active governed work. Tell me where it is stopped and what decision is required before doing anything that crosses that stop.

Expected:

- it recovers the correct active Task/current Change from bounded session state;
- it identifies the Candidate Human Stop;
- it does not scan archived history to rediscover context;
- it does not launch another Reviewer merely because the host session changed;
- it does not run Final Verification before acceptance.

Run the Candidate auditor again. `review_rounds` should remain unchanged.

## 6. Make the real human decision

Inspect the actual engineering evidence. If acceptable, explicitly approve in the conversation. Codex must record the decision through Sitter `user-review`; do not hand-edit YAML.

If you request changes, expect the Change to return to implementation and Candidate Readiness to stale. A production/semantic modification requires a new valid Candidate cycle; do not count the resulting Reviewer as duplicate ceremony.

## 7. Continue through Final Verification and closure

After approval, tell Codex to continue the accepted task normally.

Expected normal behavior:

- it actually runs the required Final Verification;
- it submits the results as one `--verification-batch` to `complete-after-approval`;
- engineering failure stops immediately;
- zero Knowledge is explicitly deferred without user ceremony;
- real Knowledge candidate stops for authority instead of being discarded;
- cleanup residue blocks Archive but is never silently deleted;
- zero/ordinary Learning is assessed automatically;
- mature durable Learning still requires individual curation;
- Task completion occurs only when the Work Graph has no other active Investigation/non-archived Change.

If `complete-after-approval` returns `governance-closure-pending`, resolve only the named real blocker, then rerun the coordinator **without** re-running already-valid Final Verification unless production/assurance inputs actually changed.

## 8. Audit closure

Run:

```powershell
python scripts/acceptance/v63-pr-a-audit.py `
  --project <real-project-root> `
  --change <change-id> `
  --phase closure `
  --output <real-project-root>/.agent-work/v63-pr-a-closure-audit.json
```

For a single-Change normal-success Task, expected status is `PASS` with:

- current human acceptance;
- structured Final Verification `pass` or explicitly justified `partial`;
- Knowledge `promoted` or `deferred`;
- Archive cleanup complete;
- Change archived;
- Learning closeout assessed;
- no unresolved mature Learning attention;
- owning Task completed.

`GOVERNANCE_PENDING` is acceptable only when the JSON names a real residual authority/cleanup/other-work blocker. Engineering proof must remain visible and must not be rolled back merely because governance closure is pending.

## 9. Record the cost comparison

Do not infer token savings from CLI count. Record only observable facts:

| Metric | V6.2 baseline | V6.3-A real run |
| --- | ---: | ---: |
| Parent-visible Harness interactions | real transcript count | real transcript count |
| Candidate Reviewer rounds | real evidence | auditor `review_rounds` |
| Repeated semantically identical Scout runs | real evidence | inspect completed delegations/transcript |
| Manual no-op Learning/Knowledge commands | real transcript | expected 0 normal path |
| Candidate Human Stops | 1 expected | 1 expected |
| Closure retries caused only by governance residue | measure | measure |
| Provider token usage | only if trustworthy structured metric exists | otherwise `not directly measured` |

Normal Scenario A target remains roughly 8–12 parent-visible Harness interactions, but correctness and true Human/Assurance stops take priority over hitting a number.

## 10. What counts as PR-A failure vs later evidence

Treat these as **PR A defects**:

- a new Change has no formal path from planning into implementation without hand-editing lifecycle state;
- installed Governor still drives the old command-by-command ceremony on the normal path;
- batch validation partially mutates state on malformed input;
- Final Verification crosses the Human Stop;
- a real Knowledge/Learning/cleanup blocker is silently erased;
- a valid prior engineering proof is unnecessarily repeated after a governance-only stop;
- Task completes despite other active governed work;
- Reviewer/attestation evidence is weaker than V6.2.

Treat these as potential **PR B/C/D evidence**, not automatic PR-A scope expansion:

- generic auxiliary task output is still misclassified as Production and stales the Candidate -> PR B candidate;
- trustworthy measurements show repeated Reviewer cost caused by mechanically safe cleanup only -> consider narrow PR C evidence;
- facade/compatibility layers measurably dominate maintenance or process cost -> PR D candidate.

Do not open PR B/C/D merely because the design documents mention them. Require real acceptance evidence.

## 11. Evidence to return to the V6.3-A PR

Attach or summarize:

- real project + baseline commit (no proprietary source required if sensitive);
- task/Change IDs;
- Candidate audit JSON;
- Closure audit JSON;
- Reviewer round count and attestation result;
- fresh-session continuity observation;
- parent-visible Harness interaction count;
- any real failure/blocker and whether it is PR-A defect or later-PR evidence;
- final verdict: `PASS`, `PASS WITH FOLLOW-UP EVIDENCE`, or `BLOCK`.
