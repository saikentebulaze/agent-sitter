# V6.3 Governance Compression and Complexity Paydown — Implementation Plan

## 1. Baseline and intent

V6.3 starts after V6.2 merge commit `771d159e7cc703e3bd8d573eabbcda6b2fe3504a`.

This plan is governed by:

- `Sitter-Core-Constitution.md`;
- `Sitter-Core-Asset-Register.md`;
- `Sitter-Complexity-Paydown-Map.md`.

V6.3 is not a broad capability expansion. The release should preserve Sitter's information and guarantees while reducing the amount of orchestration, repeated work, and historical layering that the parent Agent must understand.

The implementation rule is:

> **Preserve Information. Preserve Guarantees. Compress Ceremony.**

The cost rule is:

> **Use the minimum sufficient capability, and stop once the current requirement is satisfied.**

---

## 2. Release-level invariants

Every V6.3 slice must preserve all of the following:

- one Task / Investigation / Production Change governed Work Graph;
- LOW Fast Path without Task/Change/Learning/Scout ceremony;
- bounded cross-session continuity through durable state and the Active Task Index;
- recoverable Investigation claims, evidence, experiments, decisions, and remaining unknowns;
- Human Decision Authority and downstream stale detection;
- HIGH/CRITICAL independent exploration when required;
- numerical Readiness that cannot be satisfied by local unit tests alone when representative/benchmark/analytical evidence is required;
- one independent Candidate Reviewer when required;
- Candidate Human Stop before final closure;
- post-acceptance Final Verification;
- Durable Memory freshness/conflict/supersession semantics;
- Provider-neutral Governance Core with truthful Codex/Claude runtime proof;
- immutable review/delegation inputs and stale detection;
- no silent fallback, tolerance waiver, broad path ignore, or silent cleanup deletion.

A slice that cannot preserve these invariants must not be justified as a complexity reduction.

---

## 3. Hard implementation constraints

V6.3 must not:

- add `_harness_v63_impl.py` as another permanent facade layer;
- add a second Work Graph or Lite Change lifecycle;
- add a persisted `engineering_complete` state machine;
- create a generic Artifact Ownership framework;
- create a generic Delta Review dependency engine;
- rewrite Memory, Learning, or Provider architecture;
- hard-code current Codex model names into Governance Core;
- replace runtime attestation with configured intent;
- classify workspace files by extension;
- weaken the default rule `unknown workspace surface -> production`;
- require the parent Agent to manually compose a sequence Harness can deterministically own.

Compatibility readers may remain temporarily where required, but new V6.3 behavior should call authoritative domain transactions directly.

---

## 4. Target normal-path UX

### LOW

```text
locate -> act/run -> focused verification -> concise report
```

No governed artifacts are created merely because Sitter is installed or another Task exists.

### Governed work

```text
Investigation / bounded Scout when needed
        ↓
implementation + engineering verification
        ↓
prepare-candidate
        ↓
Candidate Human Stop
        ↓
complete-after-approval
        ↓
done
```

`status`, low-level readiness/verification commands, lifecycle `advance`, Knowledge defer, Learning closeout, and cleanup commands remain available for recovery/diagnostics when useful but leave the normal Agent-facing path.

# 5. Slice A — Surface and orchestration compression

## A1. Batch Candidate evidence

### Goal

Replace repeated per-criterion Agent orchestration with one validated candidate-evidence input.

### Existing authoritative logic to reuse

- `runtime/readiness.py`;
- `runtime/finalize_tests.py`;
- `runtime/change_budget_preflight.py`;
- `runtime/prepare_candidate.py`;
- `runtime/review_runner.py`;
- `runtime/change_lifecycle.py`.

### Required behavior

A batch Candidate input must be fully parsed and semantically validated before any readiness mutation.

It should be able to express, at minimum:

- results for all required Readiness criteria;
- evidence kind and evidence references;
- representative/benchmark/analytical evidence for numerical assurance where required;
- test-finalization classifications that are currently provided as retained/pre-existing decisions;
- optional exact Task-output declarations only after Slice B introduces that semantic boundary.

The implementation may choose the smallest compatible YAML shape after inspecting current structured evidence schemas. Do not create a second evidence model if the existing structures can be reused.

### Atomicity

If any batch item is invalid, no partial readiness result should be committed.

One batch should use one captured production/workspace state for all checks that are valid against the same instant.

---

## A2. True `prepare-candidate` coordinator

### Goal

Make `prepare-candidate` own the normal Candidate sequence instead of requiring the parent Agent to compose low-level commands.

### Target sequence

1. resolve Task/Change and validate current lifecycle;
2. validate the complete candidate-evidence input in memory;
3. capture reusable deterministic workspace state;
4. commit batch Readiness evidence atomically;
5. finalize test hygiene;
6. run Change Budget / scope preflight before any Reviewer execution;
7. render only the projections needed for review/user consumption;
8. freeze the Candidate Review snapshot;
9. execute the independent Provider-bound Reviewer when required;
10. re-capture relevant production state after external Reviewer execution and reject stale results;
11. record the review through the existing truthful transaction/evidence guard;
12. advance to `candidate-review`;
13. stop.

### Stop conditions

The coordinator must stop without pretending success when:

- numerical Readiness is insufficient;
- test finalization is unresolved;
- changed production/test scope exceeds the Change Budget;
- a Human Decision is unresolved;
- Reviewer execution/attestation fails;
- Reviewer blocks;
- reviewed input becomes stale.

It must not continue into Final Verification, Knowledge, Learning closeout, or archive before required user acceptance.

### Transaction model

Do not model the whole flow as one rollbackable ACID transaction across an external model execution.

Use:

- input prevalidation;
- local atomic writes;
- immutable review request/evidence artifacts;
- explicit stale checks around external execution;
- idempotent recovery from each semantic checkpoint.

---

## A3. Batch Final Verification

### Goal

Replace repeated `record-verification` calls with one validated final-verification input after Candidate acceptance.

### Required behavior

- valid only after current user acceptance when acceptance is required;
- all batch items validated before mutation;
- one current production snapshot for the batch where appropriate;
- structured results remain authoritative;
- Markdown remains projection;
- any failed required verification stops closure immediately.

---

## A4. `complete-after-approval` coordinator

### Goal

Compress normal post-acceptance closure into one semantic operation while keeping genuine human/engineering stops visible.

### Target sequence

1. prove Candidate acceptance is current;
2. record/finalize batch Final Verification;
3. stop on any engineering verification failure;
4. advance into the existing closure phase internally;
5. assess Knowledge consequences;
6. preserve real Knowledge candidates and stop only when human review/promotion is actually needed;
7. take the existing explicit zero-Knowledge path without meaningless document ceremony;
8. validate experiment/test/temporary-production cleanup without deleting user-owned files silently;
9. archive through the existing archive invariants;
10. run Learning closeout automatically when no user decision is needed;
11. preserve observations and stop if mature durable candidates require individual user curation;
12. complete the owning Task only when all other Task work items permit completion.

### Important multi-work-item rule

A successful Change closure must not complete a Task that still owns another active Investigation or Change.

### Partial success rule

A later Knowledge/Learning/cleanup stop must not roll back already-valid Final Verification. Report the engineering result and remaining governance residual separately.

---

## A5. Learning no-op automation

### Task creation

If governed Task creation requires Learning intake and intake is deterministic, perform it in-process as part of Task creation rather than requiring a separate Agent-facing command.

### Task closeout

If there are no meaningful observations/candidates requiring user attention, `complete-after-approval` should perform Learning closeout automatically.

If observations exist, preserve them.

If mature durable candidates require curation, stop and surface that real decision rather than silently discarding the information.

Do not weaken the existing Durable Memory promotion or Human Decision requirements.

---

# 6. Slice B — Workspace semantic boundary and narrow review reuse

## B1. Minimal semantic classification

### Goal

Distinguish engineering semantic role from file extension.

The minimum roles are:

```text
production
  changes governed behavior or durable production/test behavior

evidence
  proves a readiness/verification/review requirement

task-output
  user-requested auxiliary report/export/generated analysis output

harness
  Sitter-owned work/governance/runtime state
```

### Conservative resolution order

1. known Harness-owned path -> `harness`;
2. Change-owned production/test path -> `production`;
3. explicit assurance evidence reference -> `evidence`;
4. explicit exact Task-output declaration -> `task-output`;
5. unknown -> `production`.

### Persistence

Use the smallest durable Task-owned representation that survives a new session. Prefer an optional simple exact-path list/record on Task state or one bounded Task-owned manifest. Do not introduce a broad ownership taxonomy.

A Task-output declaration should contain only information needed to prove intent and identity, for example exact project-relative path plus a short purpose/evidence reference if needed.

### Restrictions

- no extension patterns;
- no global directory exclusions;
- no arbitrary tracked-source reclassification;
- no reclassification that conflicts with Change Budget ownership;
- evidence artifacts remain hash-bound to assurance even when not part of Production Snapshot;
- ambiguous classification remains production.

---

## B2. Production Snapshot / Change Budget integration

### Production Snapshot

Hash production semantics, not every unrelated auxiliary output.

Harness state remains excluded by explicit Harness ownership.

Evidence that is not production should be excluded from the production semantic hash but separately bound into the Readiness/Verification/Review evidence digests that rely on it.

### Change Budget

Budget checks operate on production/test semantic paths, not unrelated Task outputs.

A Task output must not be usable to hide an out-of-budget production edit.

---

## B3. Preflight-first review economics

Before spending Reviewer cost, deterministically reject:

- unresolved test hygiene;
- out-of-budget production/test changes;
- incomplete numerical Readiness;
- unresolved Human Decisions;
- invalid Task-output declarations;
- stale evidence references.

This should eliminate most avoidable re-review before introducing more sophisticated reuse logic.

---

## B4. Narrow mechanical review reuse

### Default

Any semantic ambiguity or real implementation change -> FULL independent Reviewer.

### Mechanical reuse is allowed only when deterministic proof establishes all of the following

- previously reviewed production semantics are unchanged;
- Design, Tasks, Change Budget, Human Decisions, Readiness contract/results, and test-finalization authority required by the previous review are unchanged;
- the prior review's semantic remediation does not remain unresolved;
- the new difference is a recognized mechanical cleanup or equivalent non-semantic surface change;
- the prior Provider-bound review evidence/attestation remains valid and replayable.

Do not mutate the frozen historical review request.

If a small resolution artifact is required, it must reference the immutable base review and record only deterministic reuse proof. It must never fabricate a new Provider review round.

### Explicit defer

Do not implement general Architecture/Scope/Numerical axis-level Delta Review in the first V6.3 implementation unless real telemetry later proves a repeated material need.

# 7. Slice C — State and process debt paydown

## C1. Demote duplicate completion fields

The first candidates are:

- `completion.implementation_complete`;
- `completion.ready_for_user_review`.

V6.3 should stop treating these as authority.

Because active V6.2 state and external readers may exist, prefer a compatibility transition:

1. define one canonical derived function from readiness/review/lifecycle facts;
2. dashboards and new logic read the derived value;
3. if legacy serialized fields must remain temporarily, write them only as compatibility projections from the canonical derivation;
4. do not require multiple mutation paths to update them independently;
5. defer complete physical schema removal to a release that intentionally owns migration.

This obtains synchronization simplification without turning V6.3 into a schema-migration release.

---

## C2. Do not remove `ready-to-archive` yet unless proof is trivial

The state is a strong candidate for eventual removal, but V6.3 should prioritize Agent-facing compression first.

`complete-after-approval` may internalize the transition so the parent Agent never manages it manually while persisted compatibility remains unchanged.

Physical lifecycle removal should happen only if archive validation, replay, legacy Change compatibility, and rollback behavior remain simpler after removal.

---

## C3. Lazy projections

Demote human-readable projections from mandatory write-on-every-step behavior.

Candidates:

- `verification.md`;
- `archive-summary.md`;
- Task/Change status Markdown;
- Knowledge review diff/projection;
- empty Knowledge-sync documents.

Render when:

- a user/Reviewer actually consumes the view;
- a meaningful lifecycle boundary requires an archive/report projection;
- a compatibility contract still requires it.

Structured evidence remains truth.

---

## C4. Shared workspace capture

Introduce the smallest immutable in-process capture needed by high-level transactions. It may carry:

- changed tracked/untracked paths;
- test candidates;
- semantic classification;
- production hash;
- reviewer-readable diff;
- Change Budget inputs.

It should be a transaction-local value object, not a new persistent framework.

Reuse it only while the workspace is known not to have changed. Re-capture after external Provider execution before accepting a review result.

---

## C5. In-process validation

Extract or call existing validation functions directly when a high-level coordinator currently starts another Python interpreter only to invoke a CLI wrapper around the same logic.

Preserve exactly the same validation semantics, including V6.2 review evidence guards.

Do not remove subprocess boundaries that are required for real Provider/runtime isolation.

---

## C6. Failure taxonomy

At minimum distinguish:

- `process_spawn_failure` — a Sitter-owned child process could not start;
- `command_exit_failure` — it started but the helper/runtime command returned nonzero;
- `engineering_test_failure` — the engineering verification itself failed.

A host failure that prevents Harness from starting cannot truthfully be counted as a Harness-observed spawn failure without host integration.

---

## C7. Minimal telemetry

Use one small Harness-owned Task-local record, not a tracing platform.

Track only enough to compare V6.2 and V6.3 behavior, such as:

- Harness CLI entries;
- high-level transaction invocations;
- Scout runs by role/capability grade;
- Reviewer runs;
- mechanical reuses;
- Sitter-owned subprocess launches;
- observed spawn/exit failures;
- transaction durations;
- optional Provider token usage only when returned as trustworthy structured data.

Do not persist prompts, transcripts, or large trace payloads for telemetry.

Telemetry must not affect correctness or archive eligibility when absent.

---

# 8. Slice D — Compatibility debt paydown

## D1. Inventory before deletion

Inspect actual call sites for at least:

- `harness.py -> _harness_v62_impl.py -> _harness_impl.py`;
- `work.py -> _work_impl.py` resolver monkeypatching;
- `learning.py -> _learning_impl.py` and `learning_ref_compat.py`;
- top-level Codex runtime compatibility re-exports;
- `launch_scout.py` and legacy external Scout fallback paths;
- old native/fallback interfaces superseded by Provider-bound governed execution.

Classify each as:

1. external supported caller exists -> retain a thin documented shim;
2. only internal tests/callers remain -> migrate them, then retire;
3. no caller remains -> delete.

## D2. Flatten forward, not backward

New high-level coordinators call authoritative domain APIs directly.

Do not route new behavior through historical CLI facades simply to avoid touching the internal boundary.

The public CLI may remain stable while implementation layering is reduced beneath it.

# 9. Minimum Sufficient Capability implementation

## 9.1 Deterministic first

Mechanical state, hashing, path ownership, freshness, stale detection, lifecycle legality, and evidence completeness should remain deterministic.

Do not spend model tokens on facts Harness can calculate exactly.

## 9.2 Role capability economics

Use existing Provider-neutral role/profile concepts rather than create a scheduler.

Intent by role:

- Locator / simple Memory filtering -> cheapest sufficient capability, low reasoning;
- Context/Test Scout -> cheap-to-mid capability with bounded reasoning;
- Framework Scout -> mid-tier/stronger reasoning when cross-module semantics require it;
- Maintainer Reviewer -> sufficiently strong independent reviewer;
- Deep Reviewer -> strongest tier only after evidence shows ordinary review/exploration is insufficient.

Provider implementations map these requirements to their current native model families and subagent configuration.

## 9.3 Evidence-triggered escalation

Do not choose the strongest model solely because the Task was once HIGH.

Escalate when cheaper/deterministic work reports concrete insufficiency, for example:

- `NEED_CONTEXT` after bounded search;
- unresolved competing ownership chains;
- inconclusive evidence;
- repeated problem signature;
- ordinary reviewer cannot establish a decision.

## 9.4 Reuse valid short-term evidence

Within one Task, do not repeat a semantically identical Scout merely for ceremony when:

- the frozen authority inputs remain current;
- the relevant workspace surface remains current;
- the result is not stale;
- the new question does not require a materially different role/context.

Do not build a general cache in V6.3. Start with an admission rule that recognizes already-valid delegation evidence.

## 9.5 Parallelism

Default to one relevant Scout.

Fan out only when two or more genuinely independent unknown surfaces can each materially change the engineering decision and the latency benefit justifies added token cost.

## 9.6 Dense child output

Prefer structured child evidence packets containing paths, symbols, call chains, evidence refs, unknowns, and confidence over long narrative essays.

Human-readable narrative belongs at the user boundary.

## 9.7 Stop when sufficient

Once the current objective and assurance requirement are satisfied, do not add speculative Scouts, status checks, tests, or Reviewer rounds without new evidence requiring them.

# 10. Compatibility contract

V6.3 must remain safe for existing repositories and active work created by V6.2.

At minimum:

- old Task/Change references remain resolvable;
- existing V6.2 Candidate Readiness and Review Protocol 2 evidence remains valid;
- archived review replay remains valid;
- existing structured readiness/verification evidence is still readable;
- existing `completion.*` fields may be consumed as compatibility data but are no longer authoritative in new logic;
- old low-level commands remain available for recovery during the V6.3 transition;
- no Task is silently rebound to another Provider;
- no mixed Codex/Claude Task orchestration is introduced;
- absence of new semantic-output metadata means conservative V6.2 behavior, not silent exclusion;
- absence of telemetry does not affect correctness.

Ambiguity falls back to the stricter V6.2 behavior.

# 11. Suggested PR sequence

Implementation should remain incremental and mergeable.

### PR A — Normal-path compression

- batch Candidate evidence;
- `prepare-candidate` coordinator;
- batch Final Verification;
- `complete-after-approval` coordinator;
- automatic no-op Learning/Knowledge orchestration;
- no assurance changes.

This PR should deliver the largest user-visible/Agent-visible simplification first.

### PR B — Workspace semantic boundary

- minimal exact-path Task output representation;
- `production / evidence / task-output / harness` resolution;
- Production Snapshot and Change Budget integration;
- evidence hash binding;
- preflight regression coverage.

Add narrow mechanical reuse only after the semantic boundary is proven.

### PR C — State/process paydown

- derive/demote completion projections;
- lazy projections;
- shared workspace capture;
- in-process validation;
- failure taxonomy;
- minimal telemetry.

### PR D — Compatibility paydown

- inventory consumers;
- migrate internal callers;
- remove dead facades/re-exports/fallback entrypoints;
- flatten the public CLI implementation without changing its supported semantics.

Do not bundle all four slices into one large PR.

# 12. Definition of done

V6.3 is complete only when both sides are demonstrated:

## Quality side

All Core Asset Register safety tests remain green, including fresh-session continuity, Investigation recovery, Human Authority, Memory freshness, LOW Fast Path, numerical Readiness, independent Reviewer, Candidate Human Stop, post-approval Final Verification, Provider attestation, and archived evidence replay.

## Cost side

For the same representative governed task, V6.3 demonstrates materially fewer parent-visible Harness interactions and fewer unnecessary Reviewer/process invocations than the V6.2 baseline.

Do not claim token savings unless trustworthy token accounting is available. Otherwise report measurable proxies such as Harness interactions, model invocations by role, packet sizes, subprocess launches, and wall-clock duration.
