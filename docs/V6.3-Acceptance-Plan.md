# V6.3 Governance Compression and Complexity Paydown — Acceptance Plan

## 1. Purpose

V6.3 is successful only if it proves both:

1. **core behavior and assurance are not weakened**;
2. **the same engineering objective requires less governance overhead.**

A reduction in CLI calls, Reviewer runs, model tokens, or latency does not count as success if it loses long-task continuity, engineering evidence, Human Decision Authority, numerical assurance, Reviewer independence, Memory freshness, or Provider runtime truthfulness.

This plan therefore separates **quality regressions** from **cost regressions**.

---

## 2. Acceptance levels

Reuse the existing Sitter evidence hierarchy rather than invent a new one.

### L1/L2 — deterministic and integration evidence

Prove schema, transaction, lifecycle, stale detection, workspace semantics, orchestration, compatibility, and cost counters using unit/integration tests and deterministic fixtures.

### L3 — real Provider runtime evidence

Use fresh Codex and Claude sessions to prove real SessionStart continuity, real read-only Scout/Reviewer execution, model/profile binding, actual runtime permission/sandbox evidence, and attestation.

Synthetic clients do not count as L3 proof.

### L4 — behavior/cost benchmark

Run the same representative engineering task under controlled V6.2 and V6.3 conditions and compare:

- quality outcome;
- evidence completeness;
- Scout/Reviewer behavior;
- parent-visible Harness interactions;
- subprocess/tool overhead;
- latency;
- trustworthy Provider token metrics when available.

# 3. Core regression matrix

## 3.1 LOW Fast Path

### LOW-01 — bounded deterministic edit

Expected:

- no Task;
- no Change;
- no Learning lifecycle;
- no Scout;
- no Candidate Reviewer;
- focused verification only;
- concise report.

### LOW-02 — unrelated LOW request while governed Task exists

Expected:

- Active Task Index does not force continuation;
- unrelated request remains LOW;
- no automatic durable-memory load;
- no governed artifact creation.

### LOW-03 — LOW request discovers material uncertainty

Expected:

- promotion to governed work occurs only after actual uncertainty is found;
- preserved LOW work before promotion is not retroactively turned into ceremony.

---

## 3.2 Long-task and cross-session continuity

### CONT-01 — Task survives fresh session

Create a governed Task with active work, terminate the host session, start a fresh Provider session.

Expected:

- SessionStart reads only the bounded Active Task Index initially;
- the active Task can be identified/resumed;
- archived Task history is not scanned;
- Durable Memory is not eagerly loaded.

### CONT-02 — multiple active Tasks

Expected:

- no arbitrary automatic resume selection;
- continuation must match user subject/Task identity.

### CONT-03 — resume Investigation midstream

Persist claims, supporting/contradicting evidence, experiment records, remaining unknowns, and a pending decision before ending the session.

Expected:

- fresh session reconstructs the same Investigation state;
- no previous rejected/refuted hypothesis is silently rediscovered as new truth merely because the chat was lost.

### CONT-04 — resume after Candidate preparation

Expected:

- Candidate Review evidence and Human Stop remain current when inputs are unchanged;
- final closure does not run before current user acceptance.

---

## 3.3 Investigation and independent exploration

### INV-01 — HIGH Investigation requires independent exploration

Expected:

- at least one relevant independent exploration completes before a final Investigation decision when required by risk/history;
- parent may collect evidence but cannot bypass the independent exploration gate.

### INV-02 — Scout inheritance isolation

Expected:

- Scout request does not inherit the parent's desired answer/proposed patch/full conversational hypothesis when role independence is required;
- actual runtime attestation proves the expected context/runtime boundary.

### INV-03 — NEED_CONTEXT bounded supplement

Expected:

- one concrete missing context request produces a new immutable attempt;
- old attempt remains preserved;
- bounded supplement limit remains enforced.

### INV-04 — valid Scout reuse

When a semantically identical Scout result remains current against the same authority/workspace surface:

Expected:

- no second Scout is run merely for ceremony;
- existing valid delegation evidence is reused;
- changed authority/surface/question makes the old result stale or insufficient and triggers a new run.

---

## 3.4 Dynamic risk and minimum sufficient capability

### COST-01 — current risk downshift does not lower assurance

Expected:

- `current` risk may fall only after bounded remaining work is evidenced;
- `peak` does not fall;
- Production Change assurance does not fall;
- Reviewer/numerical requirements remain determined by assurance, not cleanup risk.

### COST-02 — no repeated broad exploration after downshift

Expected:

- no extra Scout/planning/policy reload instruction solely because another turn occurred;
- remaining deterministic cleanup follows the cheaper path.

### COST-03 — deterministic before model

For mechanical facts such as path classification, stale checks, hashes, lifecycle legality, and evidence completeness:

Expected:

- no model call is required.

### COST-04 — capability escalation on insufficiency

Use a cheap/narrow role that returns a concrete insufficiency such as `NEED_CONTEXT` or competing unresolved ownership chains.

Expected:

- stronger context/model capability is used only after the insufficiency is evidenced;
- successful cheap result stops escalation.

### COST-05 — parallelism admission

Expected:

- one Scout is default;
- multiple Scouts run only when independent unknown surfaces are explicitly present;
- dependent questions do not fan out pointlessly.

## 4.3 Candidate Reviewer

### REV-01 — normal Candidate

Expected:

- one independent Provider-bound Reviewer;
- Architecture / Scope / Numerical Evidence axes remain present;
- real runtime attestation/session evidence required;
- Candidate reaches Human Stop only after pass/warn under existing semantics.

### REV-02 — real implementation BLOCK

Expected:

- Reviewer blocks on a real semantic defect;
- production source repair invalidates prior review;
- one new FULL independent Reviewer is required;

Expected:

- review cannot advance;
- snapshot-only or manually authored PASS metadata is insufficient.

### REV-04 — reviewer input changes during external execution

Expected:

- post-execution re-capture detects staleness;
- result is preserved as historical evidence but not promoted as current review.

# 5. Workspace semantic boundary tests

Use multiple artifact types intentionally. Do not use one spreadsheet case as the definition of the feature.

## WS-01 — explicit auxiliary report

Examples may include `.md`, `.csv`, `.html`, `.png`, `.json`, or spreadsheet output.

Expected:

- exact Task-output declaration excludes it from Production semantics when it is truly auxiliary;
- no extension-wide behavior is introduced;
- changing that output alone does not stale a Production Candidate unless it is also assurance evidence.

## WS-02 — undeclared unknown artifact

Expected:

- defaults to `production`;
- conservative V6.2-like behavior is preserved.

## WS-03 — tracked source attempts auxiliary reclassification

Expected:

- rejected;
- production semantics cannot be hidden by Task-output metadata.

## WS-04 — evidence artifact outside production

Expected:

- excluded from Production semantic hash if appropriate;
- content hash remains bound to the Readiness/Verification/Review evidence that uses it;
- modifying the artifact stales the assurance evidence.

## WS-05 — production-facing durable test

Expected:

- remains production/test surface, not auxiliary output.

## WS-06 — Harness state

Expected:

- `.agent-work`, managed Harness state, Change/Review/Learning/Knowledge artifacts remain classified by explicit Harness semantics;
- their normal updates do not masquerade as production changes.

# 10. Compatibility paydown tests

For every facade/re-export proposed for deletion:

1. search all repository callers and tests;
2. classify supported external compatibility vs internal/dead use;
3. migrate internal callers first;
4. run the full deterministic and Provider regression suite;
5. retain a thin shim only when a supported external interface still exists.

Specific regressions should cover:

- public Harness CLI behavior;
- Task/Change reference forms;
- Codex and Claude installed runtime entrypoints;
- static regression from outside the Harness working directory;
- Windows path handling;
- provider-specific attestation imports/paths.

No `_harness_v63_impl.py` layer should appear.

# 11. Real V6.3 benchmark scenarios

The real benchmark should reuse one sufficiently complex engineering task family so V6.2/V6.3 are comparable, but include multiple scenarios so no one fixture artifact defines the design.

## Scenario A — normal complex success

Characteristics:

- initial HIGH or equivalent material uncertainty;
- one bounded independent Scout is genuinely useful;
- Investigation converges and current execution risk can downshift;
- numerical/behavioral evidence includes a representative real case;
- implementation is correct before independent review;
- one Candidate Reviewer passes;
- Candidate Human Stop works;
- post-approval Final Verification passes;
- no mature Memory candidate requires user intervention.

Target:

- one independent Candidate Reviewer;
- normally no more than 8–12 parent-visible Harness interactions across the governed lifecycle;
- no repeated Scout after bounded context is already current;
- no manual Learning/Knowledge no-op ceremony.

The exact interaction count is a target, not an excuse to hide real decisions or failures.

## Scenario B — real implementation defect

Intentionally preserve one real defect detectable by the Reviewer.

Expected:

- round 1 FULL Reviewer blocks;
- implementation is repaired;
- round 2 FULL Reviewer passes;
- no extra re-review caused only by unrelated auxiliary artifacts or closure ceremony.

## Scenario C — auxiliary output follow-up

After the Production Candidate is stable, request one or more auxiliary outputs of different types, for example report/export/plot/generated analysis artifact.

Expected:

- exact Task-output semantics apply generically;
- Production Candidate does not stale without semantic reason;
- no Reviewer is launched solely because an unrelated Task output changed;
- if the same artifact is referenced as assurance evidence, changing it correctly stales that evidence.

## Scenario D — cross-session continuation

Terminate the host at two points:

1. mid-Investigation;
2. at Candidate Human Stop.

Expected:

- fresh session recovers the correct Task/current focus from bounded state;
- no full history scan;
- no lost claims/decisions/evidence;
- no duplicate Scout/Reviewer merely because the session changed.

## Scenario E — Memory freshness

Promote or reuse a controlled durable code-bound memory, then change its validity surface.

Expected:

- recall transitions from usable fresh candidate to suspect/unknown as appropriate;
- historical memory remains a lead, not current truth.

## Scenario F — unrelated LOW work during active long Task

Expected:

- unrelated LOW request remains lightweight despite active governed state.

| Parent-visible Harness interactions | measure real baseline | normally 8–12 for Scenario A |
| Candidate Reviewer runs | real baseline | 1 normal; 2 after a real implementation block |
| Repeated semantically identical Scout runs | measure | 0 |
| Manual no-op Learning/Knowledge commands | measure | 0 normal path |
| Sitter-owned subprocess launches | measure | lower for same scenario |

# 13. Provider acceptance

## Codex

Real runtime acceptance should verify the current native/custom subagent model/profile behavior that V6.3 relies on, including actual model/reasoning/sandbox evidence rather than configuration files alone.

Cheap-vs-strong role routing may use current Codex native capabilities in the Provider, but Governance Core remains model-name neutral.

## Claude

Claude acceptance must retain its real provider-specific agent/skill/settings/hook semantics and runtime proof. Do not copy Codex model/subagent assumptions into the Core.

## Both

A repository with both Providers installed must still support coexistence while one Task remains bound to one orchestrator Provider.

No cross-Provider Task transfer or mixed orchestration is introduced.

---

# 14. Windows acceptance

Keep the existing Windows CI/runtime controls and add V6.3-specific process regressions:

- PowerShell acceptance scripts still parse;
- static regression still runs from outside Harness cwd;
- path/reference normalization remains stable;
- new high-level coordinators do not multiply Python process launches unnecessarily;
- in-process validator substitutions match historical behavior;
- process failure taxonomy is exercised on Windows fixtures where practical.

V6.3 should reduce Sitter-owned process friction, not claim to solve host/Codex sandbox process-launch failures that occur before Harness itself runs.

---

# 15. Release acceptance rule

V6.3 should not be declared complete merely because the new high-level commands work.

Release requires:

1. all Core Asset regression scenarios green;
2. Codex and Claude runtime proof unchanged or stronger;
3. fresh-session continuity proven;
4. real numerical/behavioral Candidate still requires representative evidence;
5. one normal real-task benchmark demonstrates meaningful orchestration reduction;
6. one real Reviewer-block scenario demonstrates that cost reduction does not suppress genuine review;
7. auxiliary Task-output behavior is proven across more than one file type;
8. measured scorecard is published without claiming unmeasured token savings;
9. no new permanent version facade layer is introduced.
