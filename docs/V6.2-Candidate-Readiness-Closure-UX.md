# V6.2 — Candidate Readiness & Closure UX

## 1. Purpose

V6.2 does not add a second governance graph. It closes the gap between:

- code that is merely implemented;
- code that is credible enough to consume human acceptance time;
- code that has completed final assurance and archival work.

The target behavior is:

```text
implementation
  -> Candidate Readiness evidence
  -> test finalization
  -> independent readiness review
  -> candidate-review
  -> HUMAN STOP
  -> final verification
  -> knowledge / archive closure
```

This preserves V6 Context Capability, Human Decision Authority, dynamic risk,
LOW Fast Path, and Codex/Claude runtime proof.

## 2. Lifecycle

Activated V6.2 Changes use:

```text
proposed
  -> designed
  -> approved
  -> implementing
  -> candidate-review
  -> verifying
  -> syncing
  -> ready-to-archive
  -> archived
```

`candidate-review` means the implementation is already a credible acceptance
candidate. It is not a synonym for "coding finished".

At `candidate-review` with `user_review.status: pending`, final regression,
Knowledge, Learning closeout, archival work, and additional reviewer work are
blocked. The parent Agent presents the Candidate evidence and stops.

## 3. Compatibility and activation

The Change schema remains version 4. The asset template contains the Readiness
structure but leaves `candidate_readiness_protocol` unset so historical/direct
fixtures remain readable.

Real newly-created Production Changes activate V6.2 mechanically at the
creation transaction boundary:

- `create_task --entry change`;
- Investigation -> Change pivot;
- standalone `create_change.py`.

They are written with `candidate_readiness_protocol: 1`; this does not depend on
the Agent remembering a prompt convention.

Before implementation evidence is accepted, the Readiness Contract itself is
frozen explicitly:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot freeze-readiness <change-id>
```

`freeze-readiness` records the contract digest. Legacy V5/V6 Changes without the
protocol marker remain on their existing lifecycle and review protocol.

## 4. Readiness Contract

A Readiness Contract is defined with Design/Tasks rather than after the code is
finished.

Supported assurance classes:

- `standard`: focused deterministic evidence may be sufficient;
- `behavioral`: at least integration or representative external behavior;
- `numerical`: at least representative-case, benchmark, or analytical-check.

A numerical Change cannot become Candidate Ready from local/unit tests alone.
This is intended for solver/algorithm work where the real acceptance signal is
an engineering case, analytical solution, or commercial-software comparison.

Each readiness result is recorded structurally and bound to the current
Production Snapshot:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot record-readiness <change-id> `
  --criterion <criterion-id> --result pass `
  --command-or-entry "..." --evidence "..." --observed "..."
```

Any production/test edit after that result makes it stale.

## 5. Production Snapshot

Production Snapshot v1 hashes:

- staged tracked changes;
- unstaged tracked changes;
- untracked production/test files.

It excludes Sitter-owned lifecycle state such as:

- `.agent-work/`;
- `.harness/sitter/`;
- `changes/`;
- `knowledge/`.

Therefore recording evidence or regenerating Markdown does not invalidate the
reviewed production state.

Unborn Git repositories are supported for deterministic fixtures and early
project setup.

## 6. Test Finalization

Temporary/development tests must be removed, merged, or deliberately retained
before reviewer execution.

`prepare-candidate` invokes the existing Test Finalization transaction. If a
changed test is unclassified, the command stops before any reviewer is
launched. It never guesses retention rationale or ownership.

Explicit classification remains available:

```powershell
--retain "tests/path=durable regression value"
--preexisting "tests/path=dirty before this Change"
```

## 7. Review Protocol 2

V6.2 formal Review uses Provider-neutral Review Protocol 2.

The frozen request contains:

- the Task's real orchestrator Provider;
- the configured reviewer role/profile;
- Provider-neutral model grade;
- authoritative human decision projection;
- Review Snapshot Protocol 2;
- exact review instructions;
- a Harness-frozen reviewer-readable production/test diff.

The readable diff is important for Claude: the governed Claude reviewer is
intentionally restricted to Read/Grep/Glob and does not receive Bash merely to
run `git diff`. Harness renders the same production surface for both Providers,
binds it to the Production Snapshot, and rechecks both the diff hash and the
Production Snapshot after reviewer execution.

The same frozen review packet is executed by the Provider-managed read-only
runtime. The packet is hashed before execution and checked again before runtime
evidence is attached, preventing a request/runtime TOCTOU gap.

Codex and Claude retain their real runtime semantics:

- Codex: App Server isolated read-only Agent;
- Claude: managed read-only Agent with tool/hook/session restrictions.

Provider-specific attestation remains mandatory.

The reviewer ends with a machine-readable verdict:

```yaml
sitter_review:
  architecture: pass|warn|block
  scope: pass|warn|block
  numerical_evidence: pass|warn|block
  remediation_route: implementation|awaiting-production-design|null
```

`implementation` means deterministic repair inside approved semantics/scope and
does not require human interruption. `awaiting-production-design` means a new
semantic/scope/acceptance decision is required.

## 8. Review Snapshot Protocol 2

The V6.2 reviewer is frozen against semantic inputs rather than the mutable text
of `verification.md`:

- Production Snapshot;
- Design;
- Tasks;
- Change Budget;
- Human Decision digest;
- Readiness Contract;
- Readiness evidence;
- Test Finalization evidence.

Adding broad PASS evidence after human acceptance does not invalidate the
Candidate review when those inputs remain unchanged. Production/design/decision
changes do invalidate it.

## 9. Atomic Candidate preparation

The preferred high-level transaction after required readiness results exist is:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot prepare-candidate <change-id>
```

It performs:

```text
finalize-readiness
  -> finalize-tests
  -> refresh deterministic evidence projection
  -> review --run
  -> advance to candidate-review (PASS/WARN only)
```

If test classification is unresolved, it stops before reviewer execution. If
review returns BLOCK, it stops on the recorded remediation route and does not
advance.

## 10. Human acceptance

At Candidate Ready:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot user-review <change-id> `
  --decision approved|changes-requested|not-required --evidence "..."
```

`not-required` needs explicit user evidence. The Agent may not choose it merely
to avoid interruption.

`changes-requested` returns the Change to implementation and stales Readiness.
`approved` permits the next semantic `advance` into final verification.

## 11. Final verification and evidence projection

Final evidence is recorded structurally:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot record-verification <change-id> `
  --id full-regression --kind regression --result pass `
  --command-or-entry "..." --evidence "..." `
  --observed "..." --proves "..." --does-not-prove "..."
```

For activated V6.2 Changes, structured state is authoritative.
`verification.md` and `archive-summary.md` are deterministic projections and can
be rebuilt with:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot render <change-id>
```

Manual Markdown drift does not become a second truth source.

## 12. Semantic advance

`harness advance` never accepts an arbitrary target state.

Implemented automatic transitions are:

- `implementing -> candidate-review`;
- `candidate-review -> verifying`;
- `verifying -> syncing`;
- `syncing -> ready-to-archive`.

Each transition validates its semantic prerequisites. `ready-to-archive` still
uses the existing archive transaction because archival includes file movement
and cleanup, not merely a status change.

## 13. Windows process reduction

Review recording no longer launches `python validate_change.py` as a child
process. It uses an in-process adapter over the same validator entry point and
preserves transactional rollback on validation failure.

External subprocesses remain appropriate for real work such as Git, compilers,
tests, solvers, Codex, or Claude.

## 14. CLI reference consistency

The Work and Learning entrypoints preserve their existing implementations behind
thin compatibility facades, but Task arguments now resolve consistently as any
of:

- Task ID;
- Task directory;
- `task.yaml` path.

V6.2 Change commands likewise accept Change ID, Change directory, or
`change.yaml` path through the shared reference resolver.

## 15. Real local acceptance

The decisive acceptance should use a real repository task, not only Sitter's
toy fixtures.

For a numerical/CAE task:

1. choose a real defect or algorithm change;
2. define one representative engineering case in the Readiness Contract;
3. freeze the Readiness Contract before implementation evidence;
4. let Codex implement and gather focused + representative evidence;
5. verify that unit tests alone cannot finalize Readiness;
6. run `prepare-candidate`;
7. verify the independent reviewer catches architecture/scope/numerical gaps;
8. verify Codex stops at `candidate-review` before broad final closure;
9. accept or request changes as a human;
10. only after acceptance run broad regression and final closure;
11. compare command count, token use, retries, and re-review frequency with the V5 experience.

## 16. Non-goals

V6.2 does not introduce:

- another Work Graph;
- a Lite governance lifecycle;
- cross-Provider task transfer;
- mixed Codex/Claude orchestration inside one Task;
- arbitrary import/attestation of previously spawned native Agents;
- automatic acceptance-criterion invention;
- automatic numerical tolerance relaxation;
- a new Memory architecture.
