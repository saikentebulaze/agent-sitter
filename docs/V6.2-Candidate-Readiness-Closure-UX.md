# V6.2 — Candidate Readiness & Closure UX

## 1. Purpose

V6.2 does not add a second governance graph. It closes the gap between:

- code that is merely implemented;
- code that is credible enough to consume human acceptance time;
- code that has completed final assurance and archival work.

The target behavior is:

```text
implementation
  -> Candidate Readiness evidence
  -> test finalization / scope preflight
  -> independent readiness review
  -> candidate-review
  -> HUMAN STOP
  -> final verification
  -> knowledge / cleanup / archive closure
```

This preserves V6 Context Capability, Human Decision Authority, dynamic risk,
LOW Fast Path, and Codex/Claude runtime proof.

## 2. Lifecycle

Activated V6.2 Changes use:

```text
proposed
  -> designed
  -> approved
  -> implementing
  -> candidate-review
  -> verifying
  -> syncing
  -> ready-to-archive
  -> archived
```

`candidate-review` means the implementation is already a credible acceptance
candidate. It is not a synonym for "coding finished".

At `candidate-review` with `user_review.status: pending`, final regression,
Knowledge, Learning closeout, archival work, and additional reviewer work are
blocked. The parent Agent presents the Candidate evidence and stops.

## 3. Compatibility and activation

The Change schema remains version 4. The asset template contains the Readiness
structure but leaves `candidate_readiness_protocol` unset so historical/direct
fixtures remain readable.

V6.2 Review Protocol 2 is Provider-bound through the owning Task. A Change is
therefore activated mechanically only when creation has a real Task/orchestrator
binding:

- `create_task --entry change`;
- Investigation -> Change pivot;
- `create_change.py --task-id <existing-task>`.

Those Changes are written with `candidate_readiness_protocol: 1`; this does not
depend on the Agent remembering a prompt convention. `create_change.py` rejects
a nonexistent `--task-id` before creating artifacts.

A truly standalone Change with no Task has no trustworthy Codex/Claude
orchestrator Provider to bind Review Protocol 2 to, so it deliberately remains
on the legacy lifecycle/review protocol. V6.2 does not invent a second
standalone Provider-binding mechanism merely to force activation.

Before implementation evidence is accepted, freeze the Readiness Contract:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot freeze-readiness <change-id>
```

Legacy V5/V6 Changes without the protocol marker remain on their existing
lifecycle and review protocol.

## 4. Readiness Contract

A Readiness Contract is defined with Design/Tasks rather than after the code is
finished.

Supported assurance classes:

- `standard`: focused deterministic evidence may be sufficient;
- `behavioral`: at least integration or representative external behavior;
- `numerical`: at least representative-case, benchmark, or analytical-check.

A numerical Change cannot become Candidate Ready from local/unit tests alone.
This is intended for solver/algorithm work where the real acceptance signal is
an engineering case, analytical solution, or commercial-software comparison.

Each readiness result is recorded structurally and bound to the current
Production Snapshot:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot record-readiness <change-id> `
  --criterion <criterion-id> --result pass `
  --command-or-entry "..." --evidence "..." --observed "..."
```

Any production/test edit after that result makes it stale.

## 5. Production Snapshot

Production Snapshot v1 hashes staged tracked, unstaged tracked, and untracked
production/test files. It excludes Sitter-owned lifecycle state such as
`.agent-work/`, `.harness/sitter/`, `changes/`, and `knowledge/`.

Therefore recording evidence or regenerating Markdown does not invalidate the
reviewed production state. Unborn Git repositories are supported for
deterministic fixtures and early project setup.

## 6. Test Finalization and Change Budget preflight

Temporary/development tests must be removed, merged, or deliberately retained
before reviewer execution. `prepare-candidate` invokes the existing Test
Finalization transaction; an unclassified changed test stops the transaction
before any reviewer is launched.

Explicit classification remains available:

```powershell
--retain "tests/path=durable regression value"
--preexisting "tests/path=dirty before this Change"
```

RC2 also performs a mechanical Change Budget preflight before reviewer cost.
When `allowed_files`, `allowed_modules`, or `allowed_test_changes` declare a
path-level budget, every changed tracked/untracked production/test path must fit
that surface. Out-of-budget generated XLSX/CSV/binaries or source/test files are
reported before Review instead of consuming a Reviewer round. Historical
Changes with no path-level budget retain legacy behavior rather than receiving a
new implicit scope rule.

The same preflight is applied to direct V6.2 `review <change> --run`.

## 7. Review Protocol 2

V6.2 formal Review uses Provider-neutral Review Protocol 2. The frozen request
contains the owning Task's real orchestrator Provider, configured reviewer
profile, Provider-neutral model grade, Human Decision projection, semantic
snapshot, exact review instructions, and a Harness-frozen reviewer-readable
production/test diff.

The readable diff lets governed Claude reviewers remain Read/Grep/Glob-only;
Harness need not grant Bash merely for `git diff`. The exact frozen packet is
executed by the Provider-managed read-only runtime. Codex and Claude retain their
real runtime semantics and Provider-specific attestation remains mandatory.

Protocol 2 proof is not trusted only because plausible-looking fields exist in
`change.yaml`: static `validate_change` and every semantic `advance` re-open the
frozen request, review output, attestation and runtime evidence, re-run the
Provider attestation validator, and verify Provider/role/session binding,
pre-execution request hash and frozen production-diff hash.

When a Change is archived, the frozen request remains byte-for-byte immutable.
A historical `changes/active/<id>/...` production-diff ref is resolved to the
same artifact under the current archived Change root and its original hash is
still checked; the request itself is never rewritten to make archive validation
pass.

The reviewer ends with a machine-readable verdict:

```yaml
sitter_review:
  architecture: pass|warn|block
  scope: pass|warn|block
  numerical_evidence: pass|warn|block
  remediation_route: implementation|awaiting-production-design|null
```

`implementation` means deterministic repair inside approved semantics/scope and
does not require human interruption. `awaiting-production-design` means a new
semantic/scope/acceptance decision is required.

## 8. Review Snapshot Protocol 2

The V6.2 reviewer is frozen against semantic inputs rather than mutable
`verification.md` text:

- Production Snapshot;
- Design;
- Tasks;
- Change Budget;
- Human Decision digest;
- Readiness Contract;
- Readiness evidence;
- Test Finalization evidence.

Adding broad PASS evidence after human acceptance does not invalidate the
Candidate review when these inputs remain unchanged. Production, design,
authority, or Readiness changes do invalidate it.

## 9. Atomic Candidate preparation

The preferred high-level transaction after required readiness results exist is:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot prepare-candidate <change-id>
```

It performs:

```text
finalize-readiness
  -> finalize-tests
  -> Change Budget path preflight
  -> refresh deterministic evidence projection
  -> review --run
  -> advance to candidate-review (PASS/WARN only)
```

Unclassified tests or out-of-budget production/test paths stop before reviewer
execution. A Review BLOCK stops on the recorded remediation route and does not
advance.

## 10. Human acceptance

At Candidate Ready:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot user-review <change-id> `
  --decision approved|changes-requested|not-required --evidence "..."
```

`not-required` needs explicit user evidence. The Agent may not choose it merely
to avoid interruption. `changes-requested` returns to implementation and stales
Readiness. `approved` permits the next semantic `advance` into final
verification.

## 11. Final verification and evidence projection

Final evidence is recorded structurally:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot record-verification <change-id> `
  --id full-regression --kind regression --result pass `
  --command-or-entry "..." --evidence "..." `
  --observed "..." --proves "..." --does-not-prove "..."
```

For activated V6.2 Changes, structured state is authoritative.
`verification.md` and `archive-summary.md` are deterministic projections and can
be rebuilt with:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot render <change-id>
```

Manual Markdown drift does not become a second truth source.

## 12. Syncing and explicit closure transactions

`harness advance` never accepts an arbitrary target state. Implemented automatic
transitions are:

- `implementing -> candidate-review`;
- `candidate-review -> verifying`;
- `verifying -> syncing`;
- `syncing -> ready-to-archive`.

At `syncing`, `harness status` recommends concrete executable actions rather
than an abstract state requirement.

If no durable Knowledge candidate exists:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot defer-knowledge <change-id> `
  --reason "No durable project knowledge"
```

This is explicit, requires `entries: []` and a non-empty reason, and never
silently converts a real candidate into deferred state.

Before archive, remove development experiments and temporary production files,
then prove cleanup without allowing Harness to delete them for you:

```powershell
python "$Runtime\harness.py" --project $ProjectRoot finalize-archive-cleanup <change-id> `
  --evidence "experiments inspected and removed"
```

The transaction checks the owning Task's `experiments/` directory and declared
temporary production files. Remaining artifacts BLOCK; no automatic deletion is
performed.

A `change revised after investigation` blocker is a temporary hold preventing
pre-revision assurance from closing the Change. Once current post-revision
Readiness, Review and final Verification have all been re-proved, the
`syncing -> ready-to-archive` transaction clears that historical hold while
preserving `revision_history`.

The archive transaction records lifecycle `status: archived`, moves the Change,
rebases only operational Change-local refs that moved with it, and validates the
archived Change at its final location. Failure rolls the move/state back.

## 13. Windows process reduction

Review recording no longer launches `python validate_change.py` as a child
process. It uses an in-process adapter over the same validator entry point and
preserves transactional rollback on validation failure.

External subprocesses remain appropriate for real work such as Git, compilers,
tests, solvers, Codex, or Claude. Further process/CLI compression is intentionally
left for a later governance-cost iteration rather than expanded inside RC2.

## 14. CLI reference consistency

Work and Learning entrypoints accept Task ID, Task directory, or `task.yaml`.
V6.2 Change commands accept Change ID, Change directory, or `change.yaml` via the
shared resolver.

Top-level `harness.py --help` presents historical closure commands plus the V6.2
path including `freeze-readiness`, `record-readiness`, `prepare-candidate`,
`review --run`, `user-review`, `record-verification`, `defer-knowledge`,
`finalize-archive-cleanup`, `render`, and `advance`.

`harness status` is required to keep `ACTION REQUIRED` / `allowed_next` aligned
with real runtime commands; zero-candidate Knowledge and archive cleanup have
regression coverage for that contract.

## 15. Real local acceptance

The decisive acceptance uses a real repository task, not only Sitter toy
fixtures. The first V6.2 real engineering acceptance confirmed the Candidate
Readiness, independent Reviewer and Human Stop model, and exposed two closure
holes: zero-candidate Knowledge had no defer transaction and archive cleanup had
no explicit transaction. RC2 closes those holes and adds a Task-bound regression
that runs from Candidate preparation through human acceptance, final
verification, zero-candidate Knowledge, cleanup, archive, Learning closeout and
Task completion.

For future numerical/CAE acceptance:

1. choose a real defect or algorithm change;
2. define a representative engineering case before implementation evidence;
3. gather focused + representative evidence;
4. run `prepare-candidate` and stop at `candidate-review`;
5. after human approval, run broad final verification;
6. complete explicit Knowledge/cleanup/archive closure;
7. measure reviewer count, command/process count and latency separately from
   engineering quality.

## 16. Non-goals

V6.2 RC2 does not introduce:

- another Work Graph or Lite lifecycle;
- cross-Provider task transfer or mixed orchestration;
- a standalone Provider-binding protocol for unowned Changes;
- arbitrary import/attestation of previously spawned native Agents;
- automatic acceptance-criterion invention or tolerance relaxation;
- automatic Knowledge defer or artifact deletion;
- batch evidence, delta review, telemetry, deliverable classification, dynamic
  governance-cost redesign, or post-approval one-click closure;
- a new Memory architecture.

Those governance-cost concerns are intentionally separated from RC2 rather than
expanding this release candidate after the real acceptance report.
