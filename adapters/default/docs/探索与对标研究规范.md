# 探索与商业软件对标策略

## 核心原则

探索阶段对推理、实验设计、证据和隔离严格，对代码形式适度放宽。

正式阶段对架构、职责、接口、状态和长期可维护性严格。

## 假设驱动

每个实验先记录：

- 假设；
- 若假设成立会出现的可观察预测；
- 能与其他解释区分开的实验；
- 输入模型与控制变量；
- 代码和数据位置；
- 实际结果；
- 支持、排除或仍不确定。

禁止只写“试试这样改能不能对上”。

## 实验隔离

优先顺序：

1. `.agent-work/<task-id>/experiments/`；
2. 独立脚本或独立 executable；
3. Git worktree / 实验分支；
4. 临时修改生产文件，但必须登记和可回退；
5. 编译开关仅作短期最后手段。

## 根因确认标准

候选机制应尽量满足：

1. 解释原始异常；
2. 预测至少一个新结果；
3. 排除主要替代解释；
4. 不依赖放宽容差、调参或特殊兜底；
5. 能说明商业软件行为与 Sitter 行为的差异；
6. 能指出正式职责的合理落点。

## 退出与清理

每个临时代码必须选择：

- delete：删除；
- isolate：作为非生产研究材料隔离保留；
- promote-evidence：只将算例、数据或纯公式升级为证据；
- redesign：根据结论重新设计生产实现。

实验补丁不得直接标记为正式完成。
